## d2l 第 2 章（2.2 数据预处理）环境报错与修复
- pandas 2.x 版本差异：`inputs.fillna(inputs.mean())` 会报错 `TypeError: can only concatenate str (not "int") to str`，因为新版 pandas 的 `mean()` 不再自动跳过字符串列（Alley）。修复：加 `numeric_only=True` → `inputs.fillna(inputs.mean(numeric_only=True))`。
- torch import 报 `OSError: [WinError 1114] 动态链接库(DLL)初始化例程失败`（c10.dll）。本质=VC++ 运行库缺失/版本不对。排查顺序：①重启 Jupyter 内核/服务 → ②命令行 `conda activate d2l && python -c "import torch"` 验证 → ③装 Microsoft Visual C++ Redistributable 2015–2022 x64 → ④`conda install pytorch cpuonly -c pytorch` 干净重装。notebook 里 `import torch` 之前代码无问题。
- 用户在学习 d2l 2.2：读 CSV → 数值列 fillna 均值 → 类别列 pd.get_dummies 独热 → torch.tensor 转张量。
- 环境补充：conda 配置了清华镜像源（mirrors.tuna.tsinghua.edu.cn），偶尔连不上报 `CondaHTTPError: HTTP 000 CONNECTION FAILED`。torch 本身是 pip 装的，重装/安装优先用 `pip install torch --index-url https://download.pytorch.org/whl/cpu`，别死磕 conda 镜像。当前 d2l 环境 torch 已被用户 pip uninstall，需按上面命令重装。
- 结局：在 (d2l) CLI 跑 `python -c "import torch"` 成功打印 2.13.0+cpu，证明 torch 与系统运行库均正常。原 Jupyter 里的 WinError 1114 实为 Jupyter 内核进程卡死（坏加载状态），与 torch 无关 → 重启 Jupyter 内核/服务或重开 VS Code 即可。PowerShell 里 `where` 是 Where-Object 别名，搜文件要用 `where.exe`，别被空输出误导。用户还验证了 vcruntime140/vcomp140/VCRUNTIME140_1.dll 都在 System32，排除缺运行库。
- 根因定位（PATH 诊断）：Jupyter 内核 os.environ['PATH'] 里 `envs\d2l\Library\bin`（conda 自带 vcruntime140/vcomp140/msvcp140 副本）排在 `C:\windows\system32` 之前 → Jupyter 加载 c10.dll 依赖时吃到 conda 那份不兼容副本 → 1114；CLI 因 DLL 解析路径不同而正常。修法 A：notebook 顶部 `import torch` 前加 `os.add_dll_directory(r"C:\Windows\System32")` + `os.environ['PATH'] = r"C:\Windows\System32"+os.pathsep+os.environ['PATH']`。修法 B：把 `envs\d2l\Library\bin` 下的 vcruntime140/vcomp140/msvcp140.dll 改名 .bak，强制用 System32 正版。仍不行则考虑 `sfc /scannow` 修系统文件。
- 实测：用户确认 `Library\bin` 有 vcruntime140.dll(2026/5/20) 和 msvcp140.dll(2026/5/20)，无 vcomp140.dll（那个走 System32 没问题）。修法 A 用户实测无效（印证机制：VS Code 把 Library\bin 经 AddDllDirectory 加在 System32 之前，后加的 add_dll_directory(System32) 排其后、PATH 在安全模式不参与搜索）。结论：直接走修法 B 改名，且改名后必须重启 Jupyter 内核（旧进程内存仍持有坏 DLL）。
- 修正根因：`ren` 改名 `Library\bin\vcruntime140.dll`/`msvcp140.dll` 报「不存在项」→ 那两份已不在 Library\bin；但用户 `dir` 发现 **真正的影子副本在 `envs\d2l\` 根目录**（python.exe 旁）：`envs\d2l\vcruntime140.dll`(2026/5/20) 存在，`torch\lib\` 下没有。torch 加载器用 `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`，APPLICATION_DIR(=envs\d2l) 优先级最高、先于 System32 与 add_dll_directory 条目 → 正是这份 env-root 副本抢先被 c10.dll 依赖加载。下一步：改名 `envs\d2l\` 根目录下的 vcruntime140/msvcp140/vcomp140.dll 为 .bak（强制回退 System32 正版，CLI 已证兼容），重启内核再测 `import torch`；若仍 1114 则判定 VS Code 内核 spawn 差异 → 改用 Anaconda Prompt 里 `jupyter notebook` 在浏览器跑做对照测试。
- **破案（关键转折）**：用户报告「2-1 重启内核后仍能 import torch，2-2 不能」，且 2-2.ipynb 浏览器打开报 `NotJSONError: ''`（文件为空/损坏）。结论：① 环境内核本身能加载 torch（2-1 实证），1114 不是全局故障；② 之前 2.2 代码跑在**被污染的旧 Jupyter 内核进程**里（pip uninstall torch/重装那通折腾残留），并非文件/内核配置问题；③ 2-2.ipynb 在磁盘上是空的，根本没存上。修复：用 Python 脚本重新生成干净的 `第二章/2-2.ipynb`（12 单元，含 2.2 全流程带注释 + `fillna(mean, numeric_only=True)` 修复），kernelspec 复用 2-1 的 `python3`（映射到 d2l 环境）。已验证文件合法（4770 字节、12 cells）。用户只需在 VS Code 打开 2-2 跑即可，应和 2-1 一致能 import torch。
